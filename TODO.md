## Refactors

* we currently have 2 levels of config parsing / generation that roughly correspond to access levels: GUEST and ADMIN.

GUEST maps to this command:

* get_config

ADMIN maps to these commands:

* get_network_config
* get_app_config

Within the complete config we have these top level keys:

* board -> GUEST
* app -> ADMIN
* network -> ADMIN

Within the 'board' key, we have some various things that could be cleaned up:

* urls
* version numbers
* capabilities
* melodies
* individual controller configuration

Within the app and network, we have:

* a big chunky list of config values.  better to move to each controller with its own key with "private" values

Summary of Changes:

* app + network -> merge to admin
* melodies -> move to board.controller (buzzer)
* board urls + version numbers -> move to boards.config (ConfigManager hook)
* rename board top level key to guest?
* add top level key 'app', generated by YarrboardApp with versions and urls
* add schema version for future proofing.  add to full config, guest / main config, and admin_config
  * not found / 1 -> version 1

Notes:

* client side is loaded from firmware, and firmware dynamically generates the config every time.  it does not need to handle multiple schemas of configs.  only the firmware side needs to be aware of different versions and adapt accordingly.

-----

* Asymmetric delegation — MODERATE
Board config uses hooks (loadConfigHook / generateConfigHook), but app config uses direct calls (loadAuthConfig(), generateOTAConfig(), etc.). Two different patterns for the same job creates confusion about which controllers need hooks and which don't.

++ Solution: create loadAdminConfigHook / generateAdminConfigHook and move everything to use that.

* Error propagation hole — MODERATE
loadNetworkConfigFromJSON() can return false and propagate errors. loadAppConfigFromJSON() always returns true even if sub-component loads silently fail. Partial boot with broken config becomes invisible.

++ Solution: transition everything to the brineomatic style:

* bool BrineomaticController::loadConfigHook(JsonVariant config, char* error, size_t len)
* bool Brineomatic::validateConfigJSON(JsonVariant config, char* error, size_t err_size)
* void BrineomaticController::generateConfigHook(JsonVariant output)

++ also for admin:

* bool BrineomaticController::loadConfigHook(JsonVariant config, char* error, size_t len)
* bool Brineomatic::validateConfigJSON(JsonVariant config, char* error, size_t err_size)
* void BrineomaticController::generateConfigHook(JsonVariant output)

++ general flow:

* **LOADING** - validate -> load (validate should trim invalid configs -> then we always have a valid one for loading)
* **SAVING** - validate -> if no error -> save
